## 1. Суть продукта

ORNG LED CONTROL — собственный быстрый локальный световой пульт для одного
конкретного DJ-сетапа ORNG.

Главный рабочий сценарий:

1. система включена;
2. диджей нажимает одну из 10 кнопок;
3. запускается готовое трёхминутное световое шоу;
4. шоу бесконечно повторяется;
5. выбор другой кнопки переключает пресет;
6. отдельные быстрые действия доступны без остановки основного пресета.

Это не универсальная профессиональная DMX-консоль. Пользователь не должен
работать с таймлайном, сценами, BPM, аудиоанализом или сотнями технических
параметров во время обычной работы.

Ключевые свойства:

- очень быстрое управление одним диджеем без отдельного световика;
- локальная работа без интернета;
- простая калибровка реального оборудования;
- готовые пресеты, создаваемые и изменяемые агентом через YAML;
- простой визуальный редактор собственных пресетов;
- один и тот же движок сначала работает на Windows-ноутбуке, позже — на
  Raspberry Pi.

## 2. Архитектура и границы

### 2.1 Первый рабочий этап

```text
Веб-интерфейс → Windows-ноутбук → USB-C/Ethernet → Art-Net-контроллер
→ DMX → приборы
```

На домашнем этапе без оборудования используются Mock transport и сценический
симулятор. Art-Net transport реализуется и тестируется на уровне пакета, но
реальная отправка не выдаётся за проверенную.

### 2.2 Финальная локальная схема

```text
Телефон → Wi-Fi роутер → Raspberry Pi → Ethernet → Art-Net → DMX
Физические кнопки → GPIO/input adapter → тот же движок
```

Raspberry Pi заменяет ноутбук, но не создаёт второй продукт и не требует
переписывания движка, пресетов или интерфейса.

### 2.3 Облачная инфраструктура

- Cloudflare не используется.
- Регистрация в Cloudflare не нужна.
- Облачный деплой, публичный URL, Telegram-авторизация и учётные записи не входят
  в V1.
- Основной режим — локальная сеть заведения.
- Интерфейс с телефона позднее открывается по локальному адресу вроде
  `orng-led.local` или локальному IP.
- Потеря интернета не должна влиять на свет.

### 2.4 Зафиксированный стек

- Python 3.12;
- FastAPI — API, WebSocket и локальная раздача production-сборки;
- Vue 3 + Vite + TypeScript — интерфейс;
- YAML — профили приборов, DMX patch, пространственная схема и пресеты;
- один 512-канальный DMX universe;
- Mock transport по умолчанию;
- Art-Net ArtDmx по UDP/6454 как реальный output adapter;
- расчёт общего DMX-кадра примерно 30 раз в секунду;
- обычный запуск на Windows без обязательного Docker.

Приложение должно запускаться одним понятным PowerShell-скриптом. В production
режиме пользователь не должен отдельно запускать backend и frontend.

## 3. Физический сетап

Всего 12 приборов.

### 3.1 Основное автоматическое шоу — 10 задних приборов

- 4 задних PAR, известный предварительный режим — 7 каналов;
- 4 вертикальных Pixel Bar 124;
- 2 Beam-головы.

### 3.2 Отдельный слой — 2 лицевых PAR

- направлены на лицо диджею;
- не участвуют в автоматических пресетах;
- включаются и выключаются только отдельным управлением `DJ Face`;
- имеют отдельную яркость;
- White Hit и Strobe не должны менять их состояние;
- общий Blackout выключает их вместе со всем остальным.

### 3.3 Пространственная схема

Лево/право всегда задаётся **со стороны зрителя, смотрящего на сцену**.

Для задних PAR:

1. левый внешний;
2. левый внутренний;
3. правый внутренний;
4. правый внешний.

Для Pixel Bar:

1. левый внешний;
2. левый внутренний;
3. правый внутренний;
4. правый внешний.

Beam:

- левая;
- правая.

Face PAR:

- левый;
- правый.

Должны поддерживаться семантические группы:

- все задние;
- все PAR / все Bars / обе Beam;
- левые / правые;
- внутренние / внешние;
- зеркальные пары;
- центр → края;
- края → центр;
- отдельный прибор;
- Face PAR как полностью отдельная группа.

Bars в симуляторе и семантическом движке представляются как `4 × 8` световых
сегментов. Фактическое соответствие сегментов каналам определяется на
оборудовании.

## 4. Предварительный DMX patch

Это редактируемый черновик с запасом. Он **не подтверждён оборудованием**.

| Прибор | Стартовый адрес | Предварительно зарезервировано |
|---|---:|---:|
| PAR 1 | 001 | 7 |
| PAR 2 | 008 | 7 |
| PAR 3 | 015 | 7 |
| PAR 4 | 022 | 7 |
| Beam Right | 029 | 32 |
| Beam Left | 061 | 32 |
| Bar 1 | 093 | 16 |
| Bar 2 | 109 | 16 |
| Bar 3 | 125 | 16 |
| Bar 4 | 141 | 16 |
| Face PAR 1 | 157 | 7 |
| Face PAR 2 | 164 | 7 |

Правило DMX-адресации:

```text
глобальный канал = стартовый адрес прибора + локальный канал прибора - 1
```

Например, если прибор имеет стартовый адрес `002`, его локальный канал 1
управляется глобальным каналом 2, локальный канал 2 — глобальным каналом 3.
Порядок приборов в физической DMX-цепи на адреса не влияет.

До аппаратной проверки неизвестны и должны иметь статус
`PENDING HARDWARE`:

- реальный режим и точная карта каналов PAR;
- точное количество и функции каналов Pixel Bar, включая спорные
  15-й/16-й каналы;
- точное количество и функции каналов Beam;
- dimmer, shutter, color, gobo, reset и speed ranges;
- coarse/fine pan и tilt;
- физическая ориентация и порядок сегментов Bars;
- pan/tilt home, invert, рабочие пределы и скорость Beam;
- реальный Art-Net target IP, universe и поведение контроллера при потере
  пакетов.

В конфигурации provisional-профили должны быть явно помечены
`hardware_verified: false`. Симулятор не меняет этот флаг.

## 5. Движок

### 5.1 Основные принципы

- детерминированный расчёт кадра;
- стабильный clock, не зависящий от частоты обновления UI;
- единый DMX-кадр из 512 значений `0..255`;
- пресеты описывают семантику, а не жёсткие глобальные номера каналов;
- fixture profile переводит семантику в локальные каналы прибора;
- DMX patch переводит локальные каналы в глобальный universe;
- изменение UI не должно останавливать рендер;
- Beam никогда не телепортируются между позициями: pan/tilt проходят через
  ограниченное по скорости интерполированное движение.

Пример корректного описания пресета:

```text
внутренние Bars — белая волна снизу вверх;
внешние PAR — красная плавная пульсация;
Beam — медленное зеркальное движение.
```

Пример запрещённого описания пресета:

```text
канал 109 = 255, канал 110 = 64.
```

### 5.2 Слои и приоритеты

Базовый слой — активный циклический пресет.

Поверх него:

1. `White Hit` — короткая белая вспышка задних приборов, затем автоматический
   возврат к пресету;
2. `Strobe` — только пока удерживается кнопка, затем автоматический возврат;
3. `DJ Face` — отдельное независимое состояние лицевых PAR;
4. `master brightness` — общий безопасный коэффициент яркости;
5. `Blackout` — абсолютный наивысший приоритет, все 512 каналов равны нулю.

`White Hit` и `Strobe` не изменяют выбранный пресет и не сбрасывают его время.
После окончания overlay продолжается текущий пресет.

`Blackout` — фиксируемое состояние, а не короткая вспышка: первое действие
включает его, следующее явно выключает. Пока Blackout активен, внутренний clock
пресета продолжает идти, но наружу отправляются только нули. После снятия
Blackout возвращаются текущая точка выбранного пресета и прежнее ручное
состояние `DJ Face`.

### 5.3 Strobe safety

- ручной Strobe работает по press/release, а не как toggle;
- release, потеря соединения с UI, потеря фокуса/видимости страницы или
  защитный timeout немедленно прекращают Strobe;
- начальная максимальная частота — 4 Гц;
- начальный hard timeout удержания — 8 секунд, значение находится в безопасной
  конфигурации;
- Blackout всегда сильнее Strobe;
- в setup/test режиме strobe-каналы нельзя случайно оставить активными.

### 5.4 Output safety

- при старте всегда Mock и Blackout/нулевой безопасный кадр;
- Art-Net output по умолчанию выключен;
- реальный output включается только явным действием пользователя;
- остановка приложения пытается отправить серию нулевых кадров;
- выход из raw tester сбрасывает тестовые значения;
- потеря управляющего WebSocket не должна останавливать основной пресет, но
  обязана снять удерживаемые действия;
- ошибку output нельзя маскировать статусом «підключено»;
- аппаратная проверка обязательна для подтверждения поведения контроллера при
  потере сети.

## 6. Десять пресетов

В первом полноценном результате должно быть сразу 10 готовых пресетов.

| ID | Рабочее название | Характер |
|---|---|---|
| P01 | Дуже плавний | медленные цвета и движения |
| P02 | Атмосферний | спокойная сценическая глубина |
| P03 | М'яка динаміка | мягкие волны и зеркальные пары |
| P04 | Помірний | умеренное движение и пульсация |
| P05 | Універсальний | основной сбалансированный режим |
| P06 | Ритмічний | выраженные чейзы без постоянного строба |
| P07 | Активний | быстрые рисунки и контраст |
| P08 | Енергійний | плотное движение и короткие акценты |
| P09 | Жорсткий | клубный красно-белый характер |
| P10 | Максимальний | самая высокая допустимая интенсивность |

Каждый пресет:

- имеет длительность ровно 180 секунд;
- состоит из 10 эпизодов по 18 секунд;
- бесконечно зацикливается;
- постоянно изменяется внутри эпизода, а не остаётся статичной сценой;
- отличается композицией и эффектами, а не только множителем скорости;
- не использует BPM и аудиоанализ;
- логично или плавно переходит от последнего эпизода к первому;
- поддерживает ускоренный preview полного цикла;
- доступен в симуляторе до подключения оборудования;
- до сценической проверки помечен `hardware_tuned: false`.

Короткий встроенный строб допустим только в активных пресетах и должен
подчиняться общим безопасным ограничениям. Доводка цвета, яркости, Beam limits
и реальной выразительности всех 10 пресетов завершается только на сцене.

## 7. Интерфейс

Пользовательский UI — украинский. `DMX`, `Art-Net`, `IP`, `Universe`, `FPS`,
`Pan`, `Tilt` можно не переводить.

Визуальное направление взято из TASKA, ORNG Promo и IRIS:

- чистый card-based shell;
- оранжевый accent `#FF6A00`;
- понятная иерархия поверхностей;
- короткие действия и достаточные tap targets;
- понятные loading, empty, error, disabled и connection states;
- desktop и полноценная mobile-адаптация;
- глобальные короткие toast-сообщения;
- обычному пользователю показываются результаты, а не внутренние технические
  сущности.

Для V1 используется тёмная сценическая тема. Создание light theme не должно
задерживать HOME PLAN.

В основном меню только три раздела.

### 7.1 Пульт

- 10 крупных кнопок пресетов;
- активный пресет хорошо виден;
- текущий эпизод и время цикла;
- `DJ Face` on/off;
- отдельная яркость Face PAR;
- `White Hit`;
- `Strobe` с press/release;
- крупный и однозначный `Blackout`;
- master brightness;
- статус `Mock` / `Art-Net`;
- реальное состояние output и ошибки;
- удобное управление одной рукой с телефона.

Blackout не должен быть спрятан в меню или модальном окне.

### 7.2 Пресеты

- карточки всех 10 пресетов;
- запуск;
- переименование;
- дублирование;
- редактирование;
- создание собственного простого пресета;
- ускоренный preview в симуляторе.

Редактор состоит из упорядоченных карточек-эпизодов. Основные поля:

- длительность;
- группы приборов;
- палитра;
- эффект;
- скорость;
- интенсивность;
- переход.

Разрешены добавление, удаление и изменение порядка эпизодов. Профессиональный
многодорожечный timeline не создаётся.

### 7.3 Настройка

Один пошаговый мастер:

1. `Mock` / `Art-Net`;
2. сетевой интерфейс, target IP, universe и FPS;
3. список приборов;
4. DMX patch с проверкой пересечений и выхода за канал 512;
5. редактор fixture profile;
6. raw DMX tester;
7. расположение и ориентация приборов;
8. калибровка Bars и Beam;
9. тест прибора, группы и Blackout;
10. сводка готовности.

До реальной проверки соответствующие шаги показывают
`Не перевірено на обладнанні`. Mock-проверка не превращается в аппаратную.

Raw tester — техническая поверхность. Он обязан:

- начинать с нулей;
- позволять менять один или несколько каналов;
- явно показывать глобальный канал и значение;
- иметь немедленный Blackout;
- сбрасывать значения при выходе;
- не включать Art-Net без отдельного явного разрешения.

## 8. Симулятор

Симулятор — обязательная часть HOME PLAN, а не декоративный mockup.

Он показывает:

- схематичное расположение 12 приборов;
- цвет и яркость каждого PAR;
- 8 сегментов каждого из 4 Bars;
- позицию, направление и яркость каждой Beam;
- отдельное состояние Face PAR;
- White Hit, Strobe и Blackout;
- активный пресет, эпизод и время;
- итоговый 512-канальный кадр;
- ускоренное воспроизведение полного 180-секундного цикла.

Симулятор проверяет программную логику, но не подтверждает реальные channel
profiles, цветопередачу, движения или безопасность сцены.

## 9. Физические кнопки

Движок не должен зависеть от Vue UI. Все команды проходят через общий input
contract.

Планируется 16 кнопок:

| Кнопка | Действие |
|---:|---|
| 1–10 | выбор пресета P01–P10 |
| 11 | DJ Face |
| 12 | White Hit |
| 13 | Strobe press/release |
| 14 | Blackout |
| 15 | яркость − |
| 16 | яркость + |

На HOME-этапе реализуется keyboard/mock adapter с той же семантикой. Raspberry
GPIO adapter — отдельный будущий аппаратный этап. Arduino/ESP32 не является
основным контроллером; он может понадобиться позднее только для отдельного или
беспроводного пульта.

## 11. Нефункциональные требования

- корректная работа на актуальном Windows 11;
- мобильные ширины не являются урезанным послеthought;
- конфигурация валидируется до запуска output;
- ошибки содержат понятную причину и не оставляют опасный state;
- YAML сохраняется атомарно и не портится при невалидном редактировании;
- неизвестные поля и несовместимая версия схемы не игнорируются молча;
- тесты используют виртуальные часы, где это возможно;
- runtime не зависит от внешнего API или доступа к интернету;
- секретов в проекте нет;
- логи не должны бесконечно расти;
- обычный пользователь не видит внутреннюю архитектуру и трассировки.

## 12. Non-goals V1

- Cloudflare и любой облачный backend;
- публичный удалённый доступ;
- авторизация, роли и несколько пользователей;
- Telegram-бот или Mini App;
- несколько заведений и универсальный каталог приборов;
- BPM sync, микрофон и аудиоанализ;
- AI, принимающий решения во время шоу;
- профессиональная timeline-консоль;
- запись шоу как DMX-дампа;
- мобильное нативное приложение;
- реальный Raspberry/GPIO до завершения ноутбучного hardware acceptance.

## 13. Правило изменения канона

Агент может исправить очевидную техническую ошибку только с объяснением.
Продуктовые решения не меняются молча.

Если аппаратная проверка опровергла provisional-данные:

1. записать фактическое наблюдение;
2. обновить профиль/patch;
3. изменить `hardware_verified`;
4. обновить checklist;
5. выполнить тесты;
6. создать отдельный понятный commit.
